Enterprise Employee Agent

Законченный минимальный портфолио-проект корпоративного помощника по знаниям и рабочим действиям. Первая вертикаль использует публичные материалы GitLab Handbook: сотрудник получает ответ с доказательствами и проходит контролируемый учебный workflow leave of absence.

Название описывает пользователя, а не один HR-домен. После завершения v0.1 архитектуру можно проверить вторым сценарием из IT support, procurement или другого внутреннего процесса. Расширение начинается только после воспроизводимого релиза первой вертикали.

Честная граница. Handbook направляет настоящие US leave requests в Tilt через Okta. v0.1 не имитирует эту интеграцию и не определяет юридическую eligibility. Он создаёт локальную учебную заявку и демонстрирует поиск с источниками, минимальное раскрытие данных, подтверждаемое действие и аудит.

Решение и альтернативы

A. RAG-справочник

Отвечает по Handbook с цитатами.

Плюс: быстро. Минус: не завершает рабочую задачу.

B. Детерминированная форма

Фиксированные поля создают локальную заявку.

Плюс: предсказуемо. Минус: пользователь сам разбирается в политике.

C. Knowledge + typed workflow

LLM ищет доказательства и предлагает структурированный черновик; код проверяет полномочия, поля, подтверждение и переходы.

Плюс: показывает полный agent workflow с контролируемыми границами. Минус: требует fixtures, evals и тестов.

D. Свободный multi-agent

Агенты сами выбирают поиск и инструменты.

Плюс: гибкость. Минус: добавляет сложность раньше доказанной необходимости.

Выбран подход C. v0.1 — US leave, один законченный сценарий, локальное состояние и provider-neutral LLM adapter.

Пользовательский сценарий v0.1

Вопрос→Ответ с источниками→Уточнение→Черновик vN→Подтверждение vN→Submitted→HR processing

Сотрудник из US спрашивает, как оформить отсутствие, сообщает только необходимые операционные сведения и получает ответ с точными ссылками на разрешённые фрагменты. Система не выбирает вид leave и не обещает eligibility, если источник этого не устанавливает. Перед записью она показывает версионированный черновик. Подтверждение действует только для показанной версии.

HR принимает заявку в обработку или запрашивает уточнение. Менеджер видит только даты, операционный статус и отсутствие сотрудника. В v0.1 менеджер не одобряет и не отклоняет медицинский leave: такого шага выбранный источник не устанавливает.

Доверенная модель и доступ

Роль и личность приходят из выбранной сервером demo identity, а не из текста пользователя или вывода модели. Каждая заявка имеет владельца; fixture задаёт связь manager–employee. Проверка выполняется до retrieval, перед выполнением команды и перед формированием ответа.

Поскольку GitLab corpus публичен, запрет retrieval проверяется на явно маркированных синтетических закрытых fixtures. Эти тесты доказывают работу учебного permission manifest, а не настоящую модель доступа GitLab.

Состояния и команды

Минимальная state machine: draft → submitted → processing и submitted → needs_clarification → submitted. Черновик можно отменить до отправки. Другие переходы добавляются отдельным решением после v0.1.

  • Каждая команда содержит actor, target, ожидаемую текущую версию и idempotency key.
  • Preview возвращает нормализованный черновик и его digest/version.
  • Подтверждение с устаревшей версией отклоняется; изменение полей требует нового preview.
  • Повтор команды с тем же idempotency key возвращает исходный результат и не создаёт второе событие.
  • История событий неизменяема средствами пользовательского workflow и содержит достаточно данных для аудита без сохранения скрытого chain-of-thought.

Eval-first контракт

До изменения model-dependent поведения создаётся первая версия из 10–15 вручную проверенных кейсов, чтобы рано запустить retrieval baseline. К релизу v0.1 набор расширяется примерно до 30–40 кейсов и включает held-out часть, не используемую при настройке. Кейсы покрывают обычные вопросы, недостаточные данные, неподдерживаемые выводы, попытки получить чужие данные, prompt injection, устаревшее подтверждение и повторную отправку.

Интерпретация. «0 нарушений» означает результат данного набора тестов, а не доказательство абсолютной безопасности. На маленьком наборе отчёт публикует и проценты, и абсолютные значения. Изменение порога после baseline фиксируется с причиной.

Unit и smoke tests используют детерминированный fake adapter. Отдельный live-eval вызывает настоящую модель и фиксирует model id, параметры, prompt version, corpus manifest и сырые результаты, необходимые для повторной оценки.

Портфолио-релиз v0.1

  • README объясняет проблему, границы, быстрый запуск, demo identities, архитектуру, результаты eval и ограничения.
  • Одна команда Docker Compose запускает приложение; SQLite сохраняется в именованном volume, секреты передаются через environment и не входят в образ.
  • Простой интерфейс позволяет пройти полный сценарий и визуально показывает источники, preview, подтверждение, роль и статус.
  • CI выполняет format/lint, unit, integration и offline smoke tests без платного API; live-eval запускается отдельно.
  • Корпус имеет manifest с исходным URL, лицензией, датой получения и hashes каждого файла.
  • Проверен запуск из чистого клона по README; репозиторий содержит пример конфигурации без секретов.
  • Опубликован baseline report с ошибками и известными ограничениями, а не только агрегированным score.

Критерии приёмки поведения

  • Employee проходит путь «вопрос → evidence → clarification → preview → confirmation → submitted».
  • Изменение черновика инвалидирует прежнее подтверждение; повтор idempotent-команды не создаёт дубликат.
  • HR переводит заявку в processing или needs_clarification; manager получает только разрешённую проекцию.
  • Пользователь не получает чужую заявку, синтетический закрытый фрагмент или чувствительное поле через ответ, retrieval context, историю либо лог.
  • Неподтверждаемая eligibility не выдумывается: система задаёт уточнение или направляет к Tilt/HR согласно источнику.
  • Offline smoke test доказывает полный сценарий, а live-eval создаёт воспроизводимый baseline report.
