# 0004 — The v0.1 baseline run does no retry and no repair

Status: accepted (2026-09-13)
Related: Issue #8, decision 0003, `DEVELOPMENT_FRAMEWORK.md` §10,
`docs/superpowers/specs/2026-09-13-retrieval-answer-baseline-design.md`,
`docs/superpowers/plans/2026-09-13-retrieval-answer-baseline-implementation.md`

## Decision

The Issue #8 live baseline calls the provider once per case per model. A transient provider
failure is not retried, and an answer that breaks the contract (unparseable JSON, schema
violation, citation outside the retrieved set) is not sent back for repair; the case fails and
the failure is recorded. This is a written exception to `DEVELOPMENT_FRAMEWORK.md` §10 ("bounded
retries for transient failures", "one bounded repair attempt"), made before implementation.

## Why

The run measures what the model does on the first attempt. A retry or a repair round would turn
a contract failure into a pass and hide it from the baseline, so later changes would be compared
against an inflated number. With 7–9 cases per metric, one hidden failure moves a result from
INVESTIGATE to KEEP. The run is small, sequential and owner-gated, so a transient failure costs
at most a repeated approved run, not lost production traffic.

## Consequence

- `llm/openrouter.py` and `knowledge/answer.py` do not retry or repair: one provider call per
  case per model.
- The baseline report lists every contract violation and provider error as a raw failure and
  cites this decision among its deviations.
- The exception covers the Issue #8 baseline only. When grounded answers enter the leave
  workflow (Issue #13), that path implements §10 retries and repair as the framework requires,
  and its eval reports first-attempt and after-repair results separately. Revisit this decision
  then.
