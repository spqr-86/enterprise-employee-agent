# 0005 — Structured leave-field extraction is a second, separate contract — `AnswerContract` and `answer-v1` stay frozen

Status: accepted (2026-09-22)
Related: Issue #13, `DEVELOPMENT_FRAMEWORK.md` §3/§8/§9, `experiments/issue-8/20260914T145319Z-report.md`

## Context

`AnswerContract` (`llm/contract.py`) has `clarifying_question: str | None` and nothing
structured for leave fields. `DEVELOPMENT_FRAMEWORK.md` §3 states "The model proposes an answer
and structured fields", and the architecture diagram has an `LLM answer and field extraction`
node — dropping structured extraction would silently reinterpret a source of truth. Three
options were considered for closing the gap.

## Options considered

- **Option 1 — extend `AnswerContract`/`answer-v1` with leave fields.** Rejected.
  `ANSWER_JSON_SCHEMA` is generated from `AnswerContract` (`llm/contract.py:93`) and
  `PromptTemplate.sha256` is part of every recorded live run. Changing either invalidates the
  Issue #8 baseline (`experiments/issue-8/20260914T145319Z-report.md`) and the offline knowledge
  scores, which `DEVELOPMENT_FRAMEWORK.md` §8/§9 forbids doing silently. It also conflates two
  different validation regimes: answer claims must be citation-backed; a leave *date* comes from
  the employee's own words and must never be "supported by a cited document".
- **Option 2 — no extraction at all; only `clarifying_question` + citations, fields typed in by
  the employee.** Rejected as the sole design: it contradicts `DEVELOPMENT_FRAMEWORK.md` §3 and
  the architecture diagram's extraction node. Dropping it would silently reinterpret a source of
  truth rather than making a scoped, documented exception.
- **Option 3 (chosen) — a second, independent extraction step.** New `LeaveFieldProposal`
  contract + new `prompts/leave-fields-v1/` template + new `propose_leave_fields()` call, parsed
  by `parse_field_proposal()` mirroring `parse_answer()` (JSON → pydantic → domain rule), with no
  citation requirement and no auto-application. The knowledge path stays byte-identical, so the
  #8 baseline stays valid; the field path is separately measurable; and `LeaveRequestPayload`
  re-validates every proposed value before it can become a command.

## Decision

Option 3. Hard invariants:

- The proposal is data, never authority. It carries *values only*: `start_date | None`,
  `end_date | None`, `request_type | None`, `employee_comment | None`. No command name, no
  actor, no request id, no version, no idempotency key, no "should I submit" flag.
- `missing_fields` is **computed by deterministic code** from which values are `None`, never
  read from model output (`extra="forbid"` → invented keys fail as `ViolationKind.SCHEMA`).
- A proposal becomes a `CreateDraftInput`/`ProvideClarificationInput` only through one explicit
  deterministic function, which re-validates through `LeaveRequestPayload` and fails with
  `WorkflowError(VALIDATION_FAILED)` if incomplete or invalid.
- Submission stays a separate explicit employee act on a `build_leave_preview` envelope. Nothing
  in #13 auto-confirms.

## Consequences

- The Issue #8 baseline and the offline knowledge scores stay valid unchanged: `AnswerContract`,
  `answer-v1`, and `ANSWER_JSON_SCHEMA` are untouched by this decision.
- Answering a leave-related question now costs a second model call
  (`propose_leave_fields`/`leave-fields-v1`) in addition to `answer_for_actor`'s call, when the
  caller wants structured fields rather than free-text employee input.
- Known limitation: the `leave-fields-v1` extraction prompt has no live eval yet — only the
  offline `ScriptedProvider` integration tests and this smoke journey exercise it. A live
  baseline for field extraction is future work, tracked in `PLAN.md`.
