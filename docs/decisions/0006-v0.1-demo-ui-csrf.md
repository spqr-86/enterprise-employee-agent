# 0006 — Demo UI CSRF protection: `SameSite=Strict` cookie plus Origin/Referer check

Status: accepted (2026-09-22)
Related: Issue #14, `docs/superpowers/specs/2026-09-22-issue-14-demo-ui-design.md`

## Context

Issue #14 requires an explicit CSRF decision. The demo UI keeps the selected identity in a cookie
and exposes state-changing POST routes (create, update, cancel, confirm, start processing,
request/provide clarification, switch identity). The app runs locally on `127.0.0.1`, has no
real authentication, and must work without JavaScript.

## Options considered

- **Synchronizer token per session/form.** Rejected for v0.1: it needs server-side session state
  or a signing secret, and adds a second hidden-field mechanism next to the idempotency key for
  no additional protection in a same-origin, local, unauthenticated demo.
- **`SameSite=Strict` cookie only.** Rejected as the sole control: it depends on browser
  behaviour and does not cover same-site but cross-origin requests.
- **`SameSite=Strict` cookie plus Origin/Referer check (chosen).** No secret, no JavaScript, and
  two independent controls.

## Decision

- The identity cookie `demo_identity` is `HttpOnly`, `SameSite=Strict`, `Path=/`.
- Every POST passes a dependency that requires `Origin` — or, when `Origin` is absent, `Referer`
  — to match the app's own scheme, host, and port. A missing or foreign value returns `403`
  before any `DemoApplication` call.
- The idempotency key in forms is not a CSRF token and is not treated as one.

## Consequences

- Requests from tools that send neither header (e.g. plain `curl`) are rejected on POST; tests
  set `Origin` explicitly.
- Revisit if the UI is ever served beyond localhost, behind a proxy that rewrites `Host`, or
  gains real authentication: those cases need a synchronizer token or signed sessions.
