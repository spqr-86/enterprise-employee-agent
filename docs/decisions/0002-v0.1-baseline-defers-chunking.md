# 0002 — v0.1 baseline defers chunking (amends Issue #8 scope)

Status: accepted (2026-09-13)
Related: Issue #8, decision 0001, `docs/superpowers/specs/2026-09-13-retrieval-answer-baseline-design.md`,
`docs/superpowers/specs/2026-09-13-retrieval-answer-baseline-codex-review.md`

## Decision

Issue #8's stated scope lists "deterministic chunking with stable fragment IDs" as in scope.
This decision explicitly narrows that: the v0.1 baseline ships with whole-document evidence
(per decision 0001), and chunking is deferred to a follow-up issue. This is a scope amendment on
Issue #8, not an inference from decision 0001 — 0001 was accepted under Issue #7 and does not by
itself govern Issue #8's acceptance criteria.

## Why

An independent review (Codex, 2026-09-13) of the design spec found the spec silently treated
0001 as covering Issue #8's chunking line, which it does not — this was a real gap, not a
misreading. Reassessed on the merits:

- All 14 cases in `evals/cases/v0.1.yaml` carry document-level `expected_evidence`; none require
  fragment-level citation to pass.
- The corpus is two documents (`_index.md`, `us.md`); chunking's value (discriminating within a
  long document) is not exercised by any current case.
- Building chunking now means designing chunk boundaries/IDs, rewriting all 14 cases'
  `expected_evidence` to fragment level, and re-validating Recall@k is not trivially inflated —
  work with no case driving it, on the same "no case needs this yet" basis as 0001.

## Consequence

- Issue #8's acceptance criterion "Retrieval returns stable allowed fragment IDs" is satisfied at
  document-ID granularity (`chunking_version: none-v1`), same as decision 0001 for Issue #7.
- A comment is added to Issue #8 on GitHub pointing to this decision, so the tracked issue's
  scope line and the shipped baseline don't silently diverge.
- If a future issue needs paragraph-level grounding (e.g. a long document is added to the
  corpus), both 0001 and this decision must be revisited together — the chunking work and the
  case-file rewrite are the same piece of work either time.
