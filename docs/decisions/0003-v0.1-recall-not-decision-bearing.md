# 0003 — Recall@1 is not decision-bearing in the v0.1 baseline

Status: accepted (2026-09-13)
Related: Issue #8, decisions 0001 and 0002, `DEVELOPMENT_FRAMEWORK.md` §9,
`docs/superpowers/specs/2026-09-13-retrieval-answer-baseline-design.md`,
`docs/superpowers/specs/2026-09-13-retrieval-answer-baseline-adversarial-review.md`

## Decision

The Issue #8 baseline reports Recall@1 but does not use it in the KEEP/REVERT/INVESTIGATE rule.
This is a written exception to the framework's 90% Recall@k threshold, made before the live run.

## Why

The corpus has two documents and all 7 cases with `expected_evidence` cite `us.md`. Keyword
overlap (lowercase `\w+`) ranks `us.md` first on all 7; a constant ranker that always returns
`us.md` also scores 7/7. The metric cannot distinguish working retrieval from a stub, so a 90%
gate on it would pass without testing anything. Adding distractor documents would require a
data-scope decision (`data/README.md`), which Issue #8 does not carry.

## Consequence

- The report shows Recall@1 next to the constant-ranker control, so the number is not read as
  evidence of retrieval quality.
- Retrieval in v0.1 is judged on authorization filtering, determinism and the zero-overlap rule.
- Before any retrieval change is evaluated on Recall@k, the dataset needs cases whose expected
  evidence differs between documents. Revisit this decision when such cases exist.
